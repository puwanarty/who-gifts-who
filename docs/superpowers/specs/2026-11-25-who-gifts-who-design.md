# Who Gifts Who: ออกแบบแอปจับฉลากแลกของขวัญ

วันที่: 2026-11-25

## เจตนาและเหตุผล

แอปหน้าเดียว (SPA) สำหรับจับฉลากแลกของขวัญในงานเลี้ยงสิ้นปีกับกลุ่มเพื่อน เปิดบนเครื่องเดียวที่ต่อจอใหญ่ (ทีวี/โปรเจกเตอร์) ทุกคนเดินมาที่เครื่อง แตะชื่อตัวเอง กดปุ่ม แล้วทั้งห้องลุ้นไปพร้อมกันว่าคนนั้นจะได้ซื้อของขวัญให้ใคร

เงื่อนไขพิเศษ: คนที่มาเป็นคู่ (แฟน) ต้องไม่จับได้คู่ของตัวเอง

ความสำเร็จคือ: คืนงานใช้ได้ลื่นไหล ไม่มีใครจับได้ตัวเองหรือคู่ตัวเอง ไม่ต้องสุ่มใหม่กลางงาน และช่วงกดลุ้นสนุกจนคนทั้งห้องอยากดู

## เป้าหมาย

- ผู้จัดกรอกชื่อผู้เข้าร่วมและระบุคู่ได้ก่อนเริ่ม
- ระบบสุ่มผลที่ถูกเงื่อนไขเสมอ: ไม่จับได้ตัวเอง ไม่จับได้คู่ตัวเอง ทุกคนให้ 1 คนและได้รับ 1 คน
- ผลเปิดเผยทีละคนบนจอใหญ่ พร้อมแอนิเมชัน "แกะกล่องของขวัญ"
- ใช้ได้โดยไม่ต้องมีอินเทอร์เน็ตระหว่างงาน และไม่หายถ้าเผลอรีเฟรช

## สิ่งที่ไม่ทำ (non-goals)

- ไม่มี backend, บัญชีผู้ใช้, หรือการซิงก์ข้ามอุปกรณ์
- ไม่มีโหมดเก็บผลเป็นความลับ (ผลทุกคนเห็นบนจอร่วมกัน ตามที่ตกลง)
- ไม่มีเงื่อนไขอื่นนอกจากเรื่องคู่ (เช่น ห้ามจับคนเดิมจากปีที่แล้ว)
- ไม่ห้ามกรณีสองคนจับได้กันและกัน (A→B และ B→A) เพราะไม่ผิดเงื่อนไข
- รองรับภาษาไทยอย่างเดียว ไม่ทำ i18n

## สิ่งที่ถือว่าล้มเหลวแม้จะทำงานได้ (anti-goals)

- มีคนจับได้ตัวเองหรือคู่ตัวเอง แม้เพียงครั้งเดียว
- ต้องสุ่มใหม่กลางงานเพราะคนท้าย ๆ เหลือแต่ชื่อที่จับไม่ได้
- ตัวอักษรเล็กจนคนในห้องอ่านไม่ออกจากระยะไกล
- รีเฟรชแล้วผลหาย หรือผลเปลี่ยนจากเดิม

## ข้อจำกัด

- ใช้งานบนเครื่องเดียวที่ต่อจอใหญ่เป็นหลัก
- **รองรับทุก resolution** (ผู้ใช้กำหนด) ตั้งแต่มือถือแนวตั้ง (ความกว้างขั้นต่ำ 320px) ไปจนถึงจอ 4K ทั้งแนวนอนและแนวตั้ง ไม่มี horizontal scroll ขนาดตัวอักษรและกล่องของขวัญต้องอิงขนาดจอทั้งสองด้าน (`vmin`/`clamp`) ไม่ใช่แค่ความกว้าง หน้าตั้งค่าต้องใช้ได้ดีบนมือถือ เพราะผู้จัดอาจกรอกจากมือถือ
- โฮสต์บน **GitHub Pages** (ผู้ใช้กำหนด)
- ทำงานออฟไลน์ได้หลังโหลดครั้งแรก รวมถึงฟอนต์ และรีเฟรชตอนเน็ตหลุดแล้วยังเปิดได้
- ผู้ใช้ส่วนใหญ่โต้ตอบด้วยการแตะ/คลิก ผู้จัดอาจใช้คีย์บอร์ด
- กลุ่มเพื่อน: คาดว่า 4 ถึงประมาณ 30 คน

## แนวทางที่พิจารณา

### วิธีเปิดเผยผล (ผู้ใช้เลือก: แบบ 1)

1. **เครื่องเดียวส่งต่อกันในงาน** ← เลือก. ไม่มี backend ลุ้นพร้อมกันทั้งห้อง ต้องอยู่ในงาน
2. ผู้จัดสุ่มแล้วได้ลิงก์ส่วนตัวรายคน (ผลเข้ารหัสใน URL). สุ่มล่วงหน้าได้ แต่เสียบรรยากาศลุ้นร่วมกัน
3. ทุกคนเข้าห้องจากมือถือตัวเองแบบ real-time. ต้องมี backend (Firebase/Supabase) เกินความจำเป็น

ผลเปิดให้ทั้งห้องเห็น (ผู้ใช้เลือก) จึงไม่ต้องมีกลไกซ่อนผล

### Tech stack (ผู้ใช้เลือก: แบบ 1)

1. **Vite + React + TypeScript + Motion** ← เลือก. แอนิเมชันทำง่ายด้วย Motion, ecosystem ใหญ่, แยก logic ทดสอบได้ แลกกับ dependency แอนิเมชันเพิ่ม 1 ตัว
2. Vite + Svelte + TypeScript. มี transition ในตัว bundle เล็กกว่า แต่ต้องเรียนรู้ถ้าไม่คุ้น
3. HTML ไฟล์เดียว vanilla JS. ไม่ต้อง build แต่แอนิเมชันต้องเขียนเองทั้งหมด ทดสอบยาก

### ข้อควรระวังเรื่อง GitHub Pages

- เป็น project page (`<user>.github.io/who-gifts-who/`) ต้องตั้ง `base` ใน `vite.config.ts` ให้ตรงกับชื่อ repo และตั้ง scope ของ service worker ให้ตรงกัน
- ไม่ใช้ client-side router (แอปมี phase เดียวใน state ไม่มี URL หลายหน้า) จึงไม่เจอปัญหา 404 ตอนรีเฟรชบน GitHub Pages
- `localStorage` ของทุก project page ใต้ `<user>.github.io` ใช้ origin เดียวกัน ต้องตั้ง key ให้มี namespace เฉพาะแอป เช่น `who-gifts-who:state:v1`
- service worker ต้องอัปเดตตัวเองเมื่อ deploy เวอร์ชันใหม่ (`registerType: "autoUpdate"`) แต่ต้องไม่รีโหลดหน้าเองกลางงาน ให้ใช้เวอร์ชันใหม่ในการเปิดครั้งถัดไป
- ผู้จัดต้องใช้เบราว์เซอร์และเครื่องเดียวกันตั้งแต่กรอกชื่อจนจบงาน เพราะข้อมูลอยู่ใน `localStorage` ของเครื่องนั้น (ระบุไว้ในหน้าตั้งค่าเป็นข้อความสั้น ๆ)

### Flow และหน้าจอ

สถานะของแอปมี 4 phase: `setup` → `board` ⇄ `reveal` → `summary`

**1. หน้าตั้งค่า (`setup`)**
- เพิ่ม/ลบ/แก้ชื่อผู้เข้าร่วม
- แต่ละคนเลือกคู่ได้ 0 หรือ 1 คน ความสัมพันธ์เป็นแบบสองทาง (ตั้ง A คู่ B ⇒ B คู่ A อัตโนมัติ) และคนที่มีคู่แล้วต้องไม่ปรากฏเป็นตัวเลือกคู่ให้คนอื่น
- ตรวจก่อนเริ่ม: ชื่อห้ามว่าง ห้ามซ้ำ (เทียบหลัง trim) และอย่างน้อย 2 คน
- กด "เริ่มจับฉลาก" → สุ่มผลทั้งหมดทันที (ดูหัวข้ออัลกอริทึม) → ไป `board`
- ถ้าสุ่มไม่ได้ตามเงื่อนไข ให้แสดงข้อความบอกว่าเกิดอะไรและแก้อย่างไร (เช่น "ต้องมีคนที่ไม่ได้มาเป็นคู่กันอย่างน้อย…" หรือ "เพิ่มผู้เข้าร่วมอีกอย่างน้อย 1 คน") แล้วอยู่หน้าเดิม

**2. หน้ากระดาน (`board`)**
- แสดงปุ่มชื่อคนที่ยังไม่ได้ลุ้นให้เห็นชัดและใหญ่ แสดงรายชื่อคนที่ลุ้นแล้วแยกไว้แบบเด่นน้อยกว่า
- แตะชื่อใดก็ได้ ไม่บังคับลำดับ → ไป `reveal` ของคนนั้น

**3. หน้าลุ้น (`reveal`)** ตาม mockup C ขยายเต็มจอ
- ก่อนกด: แสดง "ตาของ {ชื่อ}" + กล่องของขวัญ + ปุ่ม "กดลุ้น" + ปุ่มย้อนกลับ (กรณีแตะชื่อผิด)
- กด "กดลุ้น" (หรือ Space/Enter): กล่องสั่นแรงขึ้นเรื่อย ๆ ราว 2.4 วินาที → ฝาเด้งออก → ชื่อผู้รับลอยขึ้นตัวใหญ่ + confetti + บรรทัด "{ผู้ให้} ได้ซื้อของขวัญให้ {ผู้รับ}"
- เมื่อกดลุ้นแล้ว คนนั้นถูกนับว่าลุ้นแล้วทันที (บันทึกลง storage ก่อนเริ่มแอนิเมชัน) เพื่อไม่ให้รีเฟรชกลางแอนิเมชันแล้วลุ้นซ้ำได้
- หลังเผยชื่อ: ปุ่ม "คนต่อไป" กลับไป `board` หรือถ้าครบทุกคนแล้ว ปุ่มพาไป `summary`
- เคารพ `prefers-reduced-motion`: ข้ามการสั่น แสดงผลทันที
- ถ้ารีเฟรชระหว่างหรือหลังแอนิเมชัน: โหลดกลับมาที่สถานะกล่องเปิดแล้ว แสดงชื่อผู้รับและปุ่ม "คนต่อไป" ทันที โดยไม่เล่นแอนิเมชันซ้ำ (ผมเลือก: ห้องยังได้เห็นผลของคนนั้น)
- ชื่อที่ลุ้นแล้วบนหน้ากระดานกดซ้ำไม่ได้ ผลรวมทั้งหมดดูได้ที่หน้าสรุป (ผมเลือก)

**4. หน้าสรุป (`summary`)**
- รายการทั้งหมด "{ผู้ให้} → {ผู้รับ}"

**เริ่มใหม่**: ปุ่ม "เริ่มใหม่" ที่ไม่เด่น (เข้าถึงได้จากทุก phase หลัง setup) ต้องยืนยันก่อน แล้วกลับไป `setup` โดยเก็บรายชื่อและคู่ไว้ แต่ล้างผลสุ่มและสถานะการลุ้น
ระหว่าง `board`/`reveal` แก้รายชื่อไม่ได้ ต้องเริ่มใหม่เท่านั้น

### อัลกอริทึมสุ่ม

Input: รายชื่อผู้เข้าร่วม (id) และคู่
Output: mapping `giverId → receiverId` ที่เป็น permutation และเป็นไปตามเงื่อนไข:
- `receiver ≠ giver`
- `receiver ≠ partner(giver)`

ข้อกำหนด:
- **ถูกเงื่อนไขเสมอ**: ห้ามคืนผลที่ผิด
- **ยุติธรรม**: ทุกการจับคู่ที่ถูกเงื่อนไขควรมีโอกาสใกล้เคียงกัน
- **บอกได้แน่นอนว่าเป็นไปไม่ได้**: ห้ามตอบว่าเป็นไปไม่ได้ ถ้าจริง ๆ มีคำตอบ

แนวทาง: rejection sampling (Fisher–Yates shuffle แล้วตรวจเงื่อนไข ทำซ้ำได้ถึงจำนวนครั้งที่กำหนด) ซึ่งให้ผลกระจายแบบ uniform ถ้าเกินจำนวนครั้ง ให้ใช้ backtracking แบบสุ่มลำดับ เพื่อหาคำตอบหรือพิสูจน์ว่าไม่มีคำตอบ
ใช้ `crypto.getRandomValues` เป็นแหล่งสุ่ม และให้ฟังก์ชันรับ random source เป็นพารามิเตอร์เพื่อให้ทดสอบได้

กรณีที่เป็นไปไม่ได้ เช่น มี 2 คนเป็นคู่กัน หรือ 3 คนที่มีคู่ 1 คู่ (คนที่เหลือจะต้องรับของจากทั้งสองคน)

### ข้อมูลและการบันทึก

```ts
type Participant = { id: string; name: string; partnerId: string | null };

type AppState = {
  version: 1;
  phase: "setup" | "board" | "reveal" | "summary";
  participants: Participant[];
  assignments: Record<string, string> | null; // giverId -> receiverId
  revealedGiverIds: string[];
  currentGiverId: string | null;              // used in "reveal"
};
```

- บันทึก `AppState` ทั้งก้อนลง `localStorage` ทุกครั้งที่ state เปลี่ยน โดยใช้ key ที่มีเวอร์ชันกำกับ
- ห่อการอ่าน/เขียนด้วย try/catch ถ้าข้อมูลเสียหรืออ่านไม่ได้ ให้เริ่มจาก state ว่าง
- โหลดกลับมาแล้วต้องได้ผลเดิมทุกครั้ง ห้ามสุ่มใหม่

### การทดสอบ

- Vitest สำหรับอัลกอริทึม: รันหลายพันครั้งกับหลายขนาดกลุ่มและรูปแบบคู่ ทุกผลต้องเป็น permutation ที่ถูกเงื่อนไข, กรณีเป็นไปไม่ได้ต้องตรวจพบ, กรณีเป็นไปได้ต้องไม่ตอบว่าเป็นไปไม่ได้, ตรวจการกระจายแบบหยาบ ๆ ว่าไม่มีผู้รับคนใดถูกเลือกบ่อยผิดปกติ
